# ✅ Definition of Done (DoD), Code Review & Quality Bar

Данный документ устанавливает жесткие критерии приемки (Definition of Done), процесс код-ревью и регламент автоматизированного контроля качества для всех доработок B2B-портала Synergy.

---

## 1. Контрольный чеклист Definition of Done (DoD)

Ни одна доработка, фича или багфикс не считаются завершенными и не могут быть смерджены в ветку `main`, пока не выполнены **все** пункты данного чеклиста:

```
┌─────────────────────────────────────────────────────────────┐
│                 DEFINITION OF DONE CHECKLIST                │
├─────────────────────────────────────────────────────────────┤
│ [ ] 1. Автоматические тесты устойчивости и безопасности     │
│ [ ] 2. UI/UX валидатор верстки и тач-событий                │
│ [ ] 3. Zero-Trust аудит безопасности (Anti-IDOR / Anti-Tamper)│
│ [ ] 4. Архитектурная чистота (лимит 400 строк на файл)      │
│ [ ] 5. Отсутствие секретов и утечек учетных данных          │
│ [ ] 6. Conventional Commits сообщение                       │
│ [ ] 7. Автоматический деплой и smoke-тест на проде          │
└─────────────────────────────────────────────────────────────┘
```

### 1.1. Обязательные автоматические проверки:
Перед коммитом разработчик или ИИ-ассистент обязан локально запустить и получить 100% успешный результат:
```bash
# 1. Запуск 134+ проверок устойчивости, безопасности и контрактов API
python3 scripts/test_resilience_and_security.py

# 2. Проверка стандартов верстки ковров и мобильного взаимодействия
python3 scripts/check-ui-standards.py
```
> [!IMPORTANT]
> Если хотя бы один тест завершился ошибкой (`✖ FAIL`), коммит **запрещен**. Разработчик обязан устранить регрессию до отправки кода.

## 2. Скоринг доработок (Architectural Scorecard)

Ревьюер (тимлид или ведущий инженер) выставляет оценку по 10-балльной шкале согласно [Архитектурному манифесту](./README.md):

| Балл | Статус | Действие |
|---|---|---|
| **8.5 — 10.0** | **APPROVED** | Код соответствует стандартам Synergy Enterprise, разрешен мердж и деплой. |
| **7.0 — 8.4** | **CHANGES REQUESTED** | Незначительные замечания (нейминг, недостаточная декомпозиция, оптимизация). |
| **< 7.0** | **REJECTED** | Архитектурная деградация, нарушение принципов Zero-Trust или потеря устойчивости. |
| **P0 Блокер** | **INSTANT REJECT** | Секреты в коде, `object-cover` у ковра, доверие клиентской цене, падение автотестов. |

## 3. Стандарт сообщений коммитов (Conventional Commits)

Все коммиты должны строго следовать стандарту Conventional Commits:

```
<type>(<scope>): <описание изменений в повелительном наклонении>
```

### Допустимые типы:
- `feat`: новая функциональность (например, `feat(catalog): add size cluster quick pills`);
- `fix`: исправление бага (например, `fix(pricing): enforce anti-tamper recalculation on checkout`);
- `refactor`: изменение кода без изменения функциональности (например, `refactor(profile): decompose orders tab into subcomponents`);
- `perf`: оптимизация производительности (например, `perf(search): add trigram GIN index for sku`);
- `docs`: обновление документации или стандартов (например, `docs(standards): publish backend architecture guide`);
- `test`: добавление или исправление тестов (например, `test(resilience): add outbox retry invariants`);
- `chore`: сопутствующие технические задачи (например, `chore(deps): update supabase-js`).

## 4. Регламент автоматического деплоя (Continuous Deployment)

Согласно регламенту `AGENTS.md`:
1. После успешного прохождения автотестов и локальной проверки изменения немедленно добавляются в git:
   ```bash
   git add <файлы>
   git commit -m "feat/fix: ..."
   git push origin main
   ```
2. Vercel автоматически запускает пайплайн сборки и выкатывает обновление на продакшн (`b2b.synergy.kz`).
3. В случае непредвиденных инцидентов на боевом контуре:
   - Немедленный откат последнего коммита (`git revert HEAD && git push origin main`);
   - Либо переключение на предыдущий успешный Deployment в Vercel Dashboard в один клик.
