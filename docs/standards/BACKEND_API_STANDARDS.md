# ⚙️ Backend API, Serverless & Security Стандарты Synergy B2B Portal

Данный документ регламентирует правила проектирования и разработки серверных функций (Serverless API на базе Vercel/Node.js/TypeScript), механизмы Zero-Trust безопасности, транзакционную модель и защиту от сбоев.

---

## 1. Архитектура Serverless API и время отклика

API портала работает в среде Serverless Functions (`api/`). В бессерверной среде жизненный цикл процесса ограничен временем выполнения одного HTTP-запроса.

```
                  ┌───────────────────────────────┐
                  │       Client / Browser        │
                  └───────────────┬───────────────┘
                                  │ HTTPS
                                  ▼
┌─────────────────────────────────────────────────────────────────┐
│                    API Gateway / Serverless                     │
│                                                                 │
│  ┌──────────────┐   ┌──────────────────────┐   ┌─────────────┐  │
│  │  cors.ts     │──►│   authGuard.ts       │──►│ Rate Limiter│  │
│  │ (Whitelist)  │   │ (Zero-Trust AntiIDOR)│   │ (Upstash)   │  │
│  └──────────────┘   └──────────────────────┘   └─────────────┘  │
│                                │                                │
│                                ▼                                │
│                     ┌────────────────────┐                      │
│                     │  pricingValidator  │                      │
│                     │   (Anti-Tamper)    │                      │
│                     └──────────┬─────────┘                      │
│                                │                                │
│          ┌─────────────────────┴─────────────────────┐          │
│          ▼                                           ▼          │
│  ┌──────────────────────────────┐         ┌──────────────────┐  │
│  │ create_order_atomic (PG RPC) │         │ Circuit Breaker  │  │
│  │  - ORDER BY sku FOR UPDATE   │         │ (L1 Fast Memory) │  │
│  │  - Outbox Pattern Event      │         └─────────┬────────┘  │
│  └──────────────────────────────┘                   │           │
└─────────────────────────────────────────────────────┼───────────┘
                                                      │ 2.5s Timeout
                                                      ▼
                                            ┌──────────────────┐
                                            │ Synergy ERP 1C   │
                                            │ (kilem-khan.kz)  │
                                            └──────────────────┘
```

### 1.1. Стандарты времени отклика (Latency Invariants)
- **Таймаут синхронного вызова ERP**: строго **2.5 секунды**. Если ERP не ответила за 2.5с, портал **не падает с 504 Gateway Timeout**, а мгновенно переводит заказ в автономную Outbox-очередь со статусом `pending` и возвращает клиенту HTTP 200/202.
- **Предотвращение Serverless Runtime Freeze**:
  В бессерверных средах фоновые вызовы (например, отправка вебхуков или алертов) замораживаются сразу после возврата `res.json(...)`.
  - **Правило**: Любые критические операции обязаны либо дожидаться резолва (`await`), либо оформляться через Vercel `waitUntil(...)`, либо делегироваться в транзакционную таблицу Outbox.

## 2. Zero-Trust безопасность и защита от IDOR

Любой запрос извне считается потенциально скомпрометированным.

### 2.1. Инвариант Anti-IDOR (Insecure Direct Object Reference)
* **❌ Категорически запрещено**:
  ```typescript
  // ПЛОХО: Доверие partner_id из тела запроса или параметров URL
  const { partner_id, order_id } = req.body;
  const order = await supabase.from('orders').select('*').eq('id', order_id).eq('partner_id', partner_id);
  ```
* **✅ Обязательный стандарт**:
  Идентификатор клиента извлекается **исключительно** из верифицированного токена сессии:
  ```typescript
  // ХОРОШО: Проверка токена через authGuard
  import { requireAuth } from './lib/authGuard';
  
  export default async function handler(req, res) {
    const session = await requireAuth(req, res);
    if (!session) return; // 401 Unauthorized уже отправлен
    
    // partner_id берется СТРОГО из сессии токена!
    const effectivePartnerId = session.partner_id;
    // ...
  }
  ```

### 2.2. Защита от подмены цен (Anti-Tamper Pricing Guard)
Клиентский интерфейс передает только список товаров (`variant_id`, `quantity`).
- Сервер **никогда не верит сумме**, присланной из корзины.
- Функция `validateAndPriceOrder(...)` (`api/lib/pricingValidator.ts`):
  1. Запрашивает мастер-цены из таблицы `product_variants` по ID;
  2. Определяет скидочную категорию партнера (`price_type`: Опт 1, Опт 2, VIP);
  3. Пересчитывает физическую площадь ковра (`width * length`) и стоимость за шт / м²;
  4. Рассчитывает эталонный `totalAmount`. Если клиент попытался подменить сумму (`clientTotal !== serverTotal`), факт регистрируется как попытка взлома в `security_events`, а заказ формируется строго по эталонной серверной цене.

### 2.3. Политика CORS (Cross-Origin Resource Sharing)
* Запрещен `Access-Control-Allow-Origin: *`.
* Разрешены только доверенные домены:
  - Продакшн: `https://b2b.synergy.kz`
  - Локальная разработка: `http://localhost:5173`
  - Предпросмотр Vercel: строго по маске доверенных превью-доменов через `api/lib/cors.ts`.

### 2.4. Территориальный Anti-BOLA Scoping для региональных менеджеров
В B2B-портале региональные и линейные менеджеры (`manager_rm`, `manager_lm`) имеют доступ строго к клиентам своего филиала/территории.
- **Инвариант:** Любой API-эндпоинт, принимающий `partner_id` или `client_id` (дебиторка, живой баланс 1С, акты сверки, отмена заказов), для менеджеров обязан верифицировать привязку контрагента к данному менеджеру в БД (`profiles.manager_id === callerAuth.userId`). При несовпадении немедленно возвращается `HTTP 403 FORBIDDEN_COUNTERPARTY_SCOPE`.
- **Защита роли закупщика (`buyer`):** Закупщики клиента имеют право оформлять заказы, но не имеют доступа к финансовому балансу и взаиморасчетам компании. Попытка запроса баланса или дебиторки блокируется с кодом `403 FORBIDDEN_FINANCIAL_ACCESS`.

### 2.5. Изоляция списания кэша каталога по складам (Warehouse-Scoped Stock Decrement)
При синхронном декременте остатков в кэше каталога (`stockCacheUpdater.ts`) при оформлении заказа:
- **Инвариант:** Если клиент заказывает товар со склада Астана ($W_{81}$), остатки на складах Алматы ($W_{82}$) и Шымкента ($W_{83}$) **не должны уменьшаться**.
- Запрещено недифференцированное списание общего количества (`?? decTotal`) на все склады. Списание применяется строго к целевому складу заказа (`wId`), предотвращая ложное обнуление витрины в соседних филиалах.

## 3. Транзакционность и конкурентный чекаут (High-Concurrency & Anti-Deadlock)

Когда несколько оптовиков одновременно заказывают популярный дизайн ковра, возникает риск оверселлинга (продажи товара в минус) или дедлока базы данных.

### 3.1. Атомарная хранимая процедура `create_order_atomic`
Оформление заказа выполняется в рамках единой ACID-транзакции в PostgreSQL:
1. **Zero-Deadlock Invariant (Упорядоченная блокировка)**:
   При блокировке строк остатков (`FOR UPDATE`) они сортируются строго по SKU:
   ```sql
   SELECT id, sku, stock_quantity 
   FROM product_variants 
   WHERE id = ANY(v_variant_ids)
   ORDER BY sku ASC -- СТРОГО УПОРЯДОЧЕННО! Предотвращает взаимную блокировку
   FOR UPDATE;
   ```
2. **Проверка остатка**:
   Если хотя бы по одной позиции `stock_quantity < requested_quantity`, транзакция делает `ROLLBACK` с ошибкой `INSUFFICIENT_STOCK`.
3. **Запись в Outbox**:
   В этой же транзакции создается запись в таблице `outbox_events` для синхронизации с ERP.

### 3.2. Outbox-паттерн и асинхронная доставка
- Заказ сохраняется локально мгновенно (< 30 мс).
- Фоновый воркер `api/outbox/sync.ts` доставляет события в ERP с экспоненциальной задержкой (Exponential Backoff: 1с, 2с, 4с, 8с, 16с).
- Заказы, превысившие 5 неудачных попыток, переводятся в статус `failed_dlq` (Dead Letter Queue) с отправкой критического алерта в Telegram.

## 4. Двухуровневый Circuit Breaker

Модуль `api/lib/circuitBreaker.ts` защищает портал и ERP от лавинообразных сбоев (Cascading Failure):

```
       5 ошибок подряд
 CLOSED ──────────────► OPEN (Все запросы идут в кэш / буфер)
    ▲                      │
    │                      │ Спустя 30 секунд
    │ 1 успешный запрос    ▼
    └──────────────── HALF_OPEN (Пробный запрос к ERP)
```

1. **L1 Fast In-Memory Cache**:
   - Состояние Circuit Breaker проверяется в локальной памяти инстанса за микросекунды, исключая задержку сетевого вызова к Redis.
2. **L2 Redis Cache (Upstash)**:
   - Синхронизирует общее состояние между всеми Serverless-инстансами Vercel.

## 5. Стандарт идемпотентности (`X-Idempotency-Key`)

Любой мутирующий запрос (создание заказа, оплата, продление брони) **обязан** сопровождаться уникальным заголовком идемпотентности (UUIDv4):
```http
POST /api/erp HTTP/1.1
X-Idempotency-Key: 7b3112d1-e970-4f51-a9f8-7b9c6a1e34e5
Idempotency-Key: 7b3112d1-e970-4f51-a9f8-7b9c6a1e34e5
```
* Если сервер получает запрос с уже обработанным ключом, он возвращает сохраненный ранее результат без повторного списания остатков или создания дубля заказа.
