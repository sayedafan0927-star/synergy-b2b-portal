### БЛОК 1. ИНТЕГРАЦИОННЫЙ ШЛЮЗ ERP / 1С (INBOUND & OUTBOUND API)

* **Суть блока и текущая планка**: Обеспечивает двусторонний обмен данными между платформой «СинЭнергия» и учетными системами (1С:ERP, CRM kilem-khan.kz). Отвечает за выгрузку каталогов, сверку остатков, импорт оплат и экспорт заказов. Требуемый уровень надежности: **99.9% доступности операций оформления** (даже при недоступности учетной базы 1С).
* **Инженерный стандарт блока (DO)**:
  1. **Унифицированная маршрутизация**: Все шлюзовые маршруты обязаны иметь явный префикс `/api/...` (или `/api/v1/...`). Никаких относительных путей или динамических `include`, зависящих от `cwd`.
  2. **Изоляция сбоев (Circuit Breaker & Outbox)**:
     - Синхронный вызов внешней ERP имеет жесткий лимит времени **не более 2.5 секунд**.
     - При отказе или таймауте ERP шлюз обязан не ронять сессию клиента (HTTP 504), а переводить заказ в оффлайн-буфер (`is_buffered_offline = true`) в таблице `orders` и ставить задачу в транзакционную таблицу `outbox_events`.
     - Двухуровневый Circuit Breaker: L1 in-memory fast cache (5 сек) + L2 Redis для отсечения повторных зависших вызовов.
  3. **Строгие контракты DTO**:
     - Входящие payload (JSON/XML) обязаны проходить строгую валидацию типов и обязательных полей до выполнения первого обращения к СУБД.
     - Очистка служебных WMS-полей: складские поля ячеек (`cell`, `cell_code`, `rack`, `location`) вырезаются из клиентского DTO заказа и разрешаются сервером по правилам складов.
  4. **Идемпотентность всех мутирующих операций**:
     - Обязательная передача и проверка заголовков `X-Idempotency-Key` / `Idempotency-Key` (UUIDv4).
     - Серверный регистр идемпотентности фиксирует статус и результат ответа на 24 часа. При повторе запроса возвращается сохраненный ответ без повторного создания заказа/проводки.
  5. **Монотонное версионирование остатков (CDC)**:
     - Любое событие обновления остатков из ERP содержит монотонный таймстемп `version_timestamp`.
     - Пакеты с `version_timestamp <= current_version` отбрасываются для предотвращения перезаписи свежих данных устаревшими вебхуками.
* **Красные линии (DON'T / P0 Violations)**:
  - ❌ Синхронное ожидание ответа от 1С/ERP дольше 2.5 секунд на клиентских HTTP-потоках.
  - ❌ Прямая передача сырых глобальных массивов (`$_POST`, `$_GET`, `req.body`) в SQL без DTO-валидации.
  - ❌ Мутация состояния заказа/склада без валидного ключа идемпотентности.
  - ❌ Падение шлюза с 500/502/504 при падении 1С (нарушение автономной устойчивости).
* **Definition of Done (DoD)**:
  - [x] Входной DTO валидирован типизированной схемой с возвратом понятного 400 Bad Request при несовпадении типов.
  - [x] Реализована проверка `X-Idempotency-Key` с сохранением ответа в регистре идемпотентности.
  - [x] Тест на таймаут ERP (эмуляция задержки >2.5с): запрос завершается штатно со статусом `is_buffered_offline: true` и попаданием в Outbox.
  - [x] Присутствует проверка монотонности версии `version_timestamp` для исключения гонки вебхуков.
  - [x] Логирование каждого запроса/ответа содержит сквозной `correlation_id` / `trace_id`.

### БЛОК 2. ДВИЖОК ОСТАТКОВ И ХОЛДИРОВАНИЯ (HOLD ENGINE & STOCK ALLOCATION)

* **Суть блока и текущая планка**: Управляет физическим и забалансовым распределением товара, резервированием под оптовых клиентов, списанием и аннулированием броней. Требуемый уровень надежности: **Абсолютная защита от оверселлинга (Zero-Overselling)** при параллельных заказах.
* **Инженерный стандарт блока (DO)**:
  1. **Zero-Deadlock & Zero-Overselling Invariant**:
     - Резервирование остатков выполняется строго внутри атомарной транзакции СУБД (`create_order_atomic`).
     - Перед взятием блокировки строки номенклатуры обязательно сортируются по возрастанию SKU (`ORDER BY sku ASC FOR UPDATE`). Это математически исключает взаимные блокировки (Deadlocks) между параллельными транзакциями.
     - Проверка доступного остатка: `IF free_stock < requested_qty THEN RAISE EXCEPTION ... ROLLBACK`.
  2. **Жизненный цикл холда (Hold Lifecycle & Strict TTL)**:
     - Каждая бронь создается с явным временем истечения `hold_expires_at`:
       - Экспресс-холд корзины: **30 минут**.
       - Оптовый резерв под выставленный счет: **24 часа** (или индивидуальный лимит по договору).
     - Фоновый демон-клинер (`api/cron/expire-holds.ts`) запускается по расписанию, находит просроченные резервы и атомарно возвращает их в `free_stock`.
  3. **Четкая 4-уровневая сегрегация складских остатков**:
     - `total_stock` = `free_stock` (доступно к заказу) + `reserved_stock` (в активных холдах) + `to_ship_stock` (оплачено/собрано) + `consignment_stock` (забаланс комитентов).
     - Запрещено смешивать запасы Центрального хаба (Склад 81, Астана) и партнерских шоурумов дилеров в одном расчетном пуле без явной складской адресации.
  4. **Мгновенная Realtime-нотификация**:
     - При снятии холда или резерва платформа отправляет событие `partner_stock_released` через Supabase Realtime / WebSocket / BroadcastChannel, синхронизируя каталоги у всех активных менеджеров.
* **Красные линии (DON'T / P0 Violations)**:
  - ❌ Выполнение `UPDATE stock` без блокировки `FOR UPDATE` или оптимистической блокировки `version`.
  - ❌ Возникновение отрицательного остатка (нарушение `CHECK (free_stock >= 0)`).
  - ❌ Бессрочные холды (отсутствие `hold_expires_at` или отключенный клинер).
  - ❌ Смешивание собственного складского запаса и комиссионного товара в единую цифру без признака права собственности.
* **Definition of Done (DoD)**:
  - [x] Резервирование выполняется через транзакционную процедуру `create_order_atomic` с `ORDER BY sku ASC`.
  - [x] В БД активны CHECK-констрейнты `free_stock >= 0` и `reserved_stock >= 0`.
  - [x] Установлен TTL бронирования с автоматическим высвобождением через планировщик.
  - [x] Реализована широковещательная Realtime-рассылка события изменения остатка.
  - [x] Стресс-тест на 50 параллельных потоков на один и тот же SKU не создает оверселлинга и дедлоков.

### БЛОК 3. ФИНАНСОВЫЙ БАЛАНС И КАЛЬКУЛЯЦИЯ КАПИТАЛА (FINANCIAL ENGINE)

* **Суть блока и текущая планка**: Обеспечивает непрерывный управленческий учет (`financial_dashboard.php`), калькуляцию Чистого Капитала ($\text{Equity} = \text{Assets} - \text{Liabilities}$), контроль кредитных плеч оптовиков, учет займов и мультивалютную оценку (USD / KZT). Требуемый уровень надежности: **Нулевая финансовая погрешность (Zero Financial Discrepancy)**.
* **Инженерный стандарт блока (DO)**:
  1. **Исключение чисел с плавающей точкой (No Floats)**:
     - Все финансовые величины в СУБД хранятся строго в типе `DECIMAL(18, 4)` (или `DECIMAL(15, 2)` для фискальных сумм).
     - Все расчеты на бэкенде ведутся через библиотеку произвольной точности **BCMath** (`bcadd`, `bcsub`, `bcmul`, `bcdiv` с масштабом округления 4 знака).
     - В клиентском слое вычисления производятся в целых единицах (тиыны/центы) либо с использованием библиотек типа `big.js`, с банковским округлением (Half-to-even).
  2. **Строгая изоляция забаланса (Off-Balance Sheet Isolation)**:
     - Комиссионные остатки товаров внешних поставщиков учитываются исключительно на забалансовых регистрах.
     - **Категорически запрещено включать себестоимость забалансовых товаров в строку собственных Активов.** Капитал компании не должен фиктивно раздуваться за счет чужого товара.
  3. **Отказоустойчивый дашборд (Fault-Tolerant Dashboard Engine)**:
     - Загрузка виджетов баланса (Дебиторка, Склад, Касса, Займы, Кредиторка) производится параллельно через `Promise.allSettled`.
     - При недоступности любого отдельного API-источника (например, тайм-аут Firebase по займам или сбой сервиса дебиторки):
       - Упавший виджет отображает значение `0.00` с предупреждающей плашкой `[Данные временно недоступны]`.
       - Ошибка логируется в телеметрию/консоль.
       - Формула баланса и остальные карточки дашборда **продолжают рендериться без белого экрана (WSOD)**.
  4. **Фиксация валютного курса транзакции**:
     - Базовая цена контракта фиксируется в USD, операционная оплата — в KZT.
     - Каждый заказ и финансовая проводка обязаны сохранять неизменяемый курс валюты на момент совершения операции (`applied_exchange_rate`).
  5. **Контроль совокупного кредитного плеча**:
     - Валидация кредитного риска: $\text{Effective Exposure} = \text{Current Debt} + \text{New Order Amount} \le \text{Credit Limit}$.
     - При превышении лимита заказ блокируется для авто-отгрузки и направляется на согласование финансовому директору через WhatsApp-шлюз.
* **Красные линии (DON'T / P0 Violations)**:
  - ❌ Использование типов `FLOAT`, `DOUBLE` или `REAL` для денежных полей в схемах таблиц.
  - ❌ Ошибки округления и прямое сложение `0.1 + 0.2` в JS на экранах финансовой отчетности.
  - ❌ Включение комиссионного товара в балансовые активы при расчете собственного капитала.
  - ❌ Полный сбой рендера финансового экрана при сетевой ошибке одного из 5 микровиджетов.
  - ❌ Изменение `applied_exchange_rate` в уже проведенном заказе задним числом.
* **Definition of Done (DoD)**:
  - [x] Все финансовые колонки имеют тип `DECIMAL` с CHECK-констрейнтами неотрицательности сумм.
  - [x] Серверные финансовые калькуляции выполняются с использованием `BCMath`.
  - [x] Забалансовые остатки комитентов отделены от балансовых активов в SQL и UI.
  - [x] Дашборд протестирован на отключение одного из источников: интерфейс не падает, отдавая graceful fallback = 0.
  - [x] Проверка формулы `Effective Exposure <= Credit Limit` выполняется до фиксации заказа.

### БЛОК 4. КАБИНЕТ ПОСТАВЩИКА-КОМИССИОНЕРА (SUPPLIER & CONSIGNMENT ENGINE)

* **Суть блока и текущая планка**: Обеспечивает учет движения товаров комитентов, приход на ответственное хранение, формирование отчетов комиссионера (`commissioner_report.php`), расчет комиссионного вознаграждения и акты взаиморасчетов. Требуемый уровень надежности: **100% юридическая и учетная прозрачность начислений**.
* **Инженерный стандарт блока (DO)**:
  1. **Момент признания обязательства (Post-Sale Debt Recognition)**:
     - Приемка товара от комитента на склад оформляется со статусом «Ответственное хранение» (`in_custody = true`).
     - **В момент приемки кредиторская задолженность платформы перед комитентом строго равна 0.00.**
     - Финансовое обязательство (долг к выплате) возникает **исключительно по факту продажи и отгрузки конечному покупателю** (событие `order.status = 'completed'` или `'shipped'`).
  2. **Прозрачность формулы вознаграждения в реальном времени**:
     - В кабинете поставщика отображается полная детализация:
       $$\text{Сумма к выплате} = \text{Цена реализации} - \text{Комиссионное вознаграждение платформы} - \text{Услуги доставки/обработки}$$
     - Ставка комиссии фиксируется по договору (в процентах или фиксированной суммой за кв. метр).
  3. **Сегрегация прав собственности в складском интерфейсе**:
     - Каждая единица номенклатуры комиссионера четко маркируется в UI:
       - «На ответственном хранении» (доступно для выставления в каталог).
       - «В резерве покупателя» (забронировано в активном заказе).
       - «Реализовано» (включено в отчет комиссионера к выплате).
       - «Брак / Возврат комитенту» (выведено из оборота).
  4. **Неизменяемость закрытых отчетов (Immutable Acts)**:
     - Сформированный за отчетный период (месяц/квартал) акт комиссионера подписывается и сохраняется в виде неизменяемого снепшота (Read-Only JSON + PDF).
     - Повторная переоценка цен или скидок каталога не может влиять на уже закрытые акты.
* **Красные линии (DON'T / P0 Violations)**:
  - ❌ Начисление долга перед поставщиком в момент поступления партии на склад.
  - ❌ Скрытие формулы расчета комиссии (отображение только финальной цифры без ставки и базы).
  - ❌ Возможность продажи комиссионного товара без привязки `supplier_id` и признака `is_consignment: true`.
  - ❌ Модификация строк закрытого отчета комиссионера после его подписания.
* **Definition of Done (DoD)**:
  - [x] Приходная накладная комиссионера создает забалансовые остатки без начисления финансового долга.
  - [x] Триггер начисления задолженности срабатывает только при статусе заказа `shipped`/`completed`.
  - [x] В UI поставщика реализован разбор формулы «Продажи – Комиссия = К выплате».
  - [x] Зафиксирован статус неизменяемости (Lock) для утвержденных отчетов комиссионера.
  - [x] Тесты подтверждают изоляцию бракованных позиций от доступного к продаже остатка.

### БЛОК 5. КОРПОРАТИВНАЯ БЕЗОПАСНОСТЬ И MULTI-TENANCY (SECURITY & RBAC)

* **Суть блока и текущая планка**: Обеспечивает защиту коммерческой тайны (базы дилеров, индивидуальные скидочные матрицы, закупочные цены, условия комитентов) и разграничение доступа между ролями (Дилер, Менеджер, Поставщик, Администратор). Требуемый уровень надежности: **Банковский стандарт изоляции данных (Zero-Trust Multi-Tenancy)**.
* **Инженерный стандарт блока (DO)**:
  1. **Zero-Trust Identity & Anti-IDOR Invariant**:
     - Идентификаторы арендатора (`partner_id`, `supplier_id`, `client_id`, `role`) **никогда не принимаются на веру из параметров клиента** (`req.body`, `req.query`, `$_GET`, `$_POST`).
     - Контекст авторизации извлекается строго из валидированного криптографического токена/серверной сессии (`authGuard.ts`).
     - Если клиент запрашивает ресурс по ID, сервер выполняет обязательную проверку принадлежности: `WHERE id = :id AND partner_id = :session_partner_id`.
  2. **100% Параметризация всех обращений к СУБД**:
     - Полный запрет конкатенации строк при формировании SQL.
     - Использование только подготовленных выражений PDO (`$stmt = $pdo->prepare(...)`) или строго типизированных Query Builder с биндингом параметров.
  3. **Полная изоляция поставщиков и контрагентов (Cross-Tenant Isolation)**:
     - Ни при каких условиях поставщик «А» не может получить доступ к данным, остаткам, ценам или объемам продаж поставщика «Б».
     - Применение политик Row Level Security (RLS) в PostgreSQL / жестких фильтров на уровне единого репозитория данных.
  4. **Маскирование чувствительных данных (PII & Secrets)**:
     - В журналах аудита (`audit_logs`) номера телефонов, персональные данные, пароли и токены автоматически маскируются (`+7 *** *** 45 67`).
* **Красные линии (DON'T / P0 Violations)**:
  - ❌ Доверие параметру `partner_id` или `user_id`, переданному в теле запроса (IDOR-уязвимость).
  - ❌ Конкатенация строк в SQL (`"SELECT * FROM orders WHERE id = " . $id`).
  - ❌ Утечка оптовых скидок или цен одного дилера другому контрагенту.
  - ❌ Хранение открытых паролей, мастер-ключей или API-токенов в кодовой базе репозитория.
  - ❌ Доступ к административным эндпоинтам без валидации роли `is_admin = true` на бэкенде.
* **Definition of Done (DoD)**:
  - [x] Все эндпоинты защищены через `authGuard` / централизованный middleware сессий.
  - [x] Все SQL-запросы используют исключительно параметризованные Prepared Statements.
  - [x] Автотесты на подмену ID (IDOR fuzzing) подтверждают возврат 403 Forbidden / 404 Not Found.
  - [x] В коде отсутствуют захардкоженные токены, пароли и приватные ключи.
  - [x] Журнал аудита маскирует PII и записывает факт каждой критической операции.

### БЛОК 6. КЛИЕНТСКИЙ СЛОЙ, UX И ИНТЕРФЕЙС БЕЗ БАГОВ (FRONTEND & PERFORMANCE)

* **Суть блока и текущая планка**: Обеспечивает высокоскоростную работу оптового каталога, интерактивных дашбордов, таблиц остатков и корзины оформления. Требуемый уровень надежности: **Субсекундный отклик интерфейса (Sub-50ms UX)** без визуальных артефактов и сбоев.
* **Инженерный стандарт блока (DO)**:
  1. **Разметка модальных окон и оверлеев (React Portals Invariant)**:
     - Все элементы с позиционированием `fixed` и `absolute` (модальные окна, дропдауны, боковые шторки, полноэкранные спиннеры, всплывающие подсказки) монтируются **строго в корень документа** (`document.body` через `createPortal`).
     - Это гарантирует, что оверлеи никогда не будут сжаты, деформированы или обрезаны родительскими контейнерами с `max-w-*`, `overflow-hidden` или CSS `transform`.
  2. **Асинхронная неблокирующая загрузка (`Promise.allSettled`)**:

     - Отображение Skeleton Loaders во время подгрузки данных вместо блокирующих оверлеев на весь экран.
  3. **Защита от дребезга (Debounce & AbortController)**:
     - Все поля живого поиска по каталогу, артикулам и клиентам обязаны использовать Debounce с задержкой **300–400 мс**.
