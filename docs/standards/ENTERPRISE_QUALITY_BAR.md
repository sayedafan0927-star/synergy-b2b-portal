### БЛОК 1. ИНТЕГРАЦИОННЫЙ ШЛЮЗ ERP / 1С (INBOUND & OUTBOUND API)

* **Суть блока и текущая планка**:  
  Обеспечивает непрерывный двусторонний обмен данными между B2B-порталом и 1С:ERP / CRM. Отвечает за прием изменений каталога, остатков и экспорт оптовых заказов. **Целевая планка: 99.9% доступности оформления заказов.** Отказ 1С не должен прерывать работу клиентов на портале.

* **Инженерный стандарт блока (DO)**:
  1. **Унифицированная маршрутизация**: Все шлюзовые маршруты обязаны иметь явный префикс `/api/v1/erp/*` (или `/api/erp.ts?action=*`). Запрещены любые относительные пути или динамические вызовы, зависящие от `cwd`.
  2. **Изоляция сбоев (Circuit Breaker & Outbox)**:
     - Синхронный вызов внешней ERP ограничен жестким лимитом времени **не более 2.5 секунд**.
     - При отказе или таймауте ERP шлюз переводит заказ в оффлайн-буфер (`is_buffered_offline = true`) в таблице `orders` и ставит задачу в таблицу `outbox_events`.
     - Двухуровневый Circuit Breaker: L1 in-memory fast cache (5 сек) + L2 Redis для синхронизации состояния между серверлесс-воркерами.
  3. **Строгие контракты DTO**:
     - Входящие payload (JSON/XML) обязаны проходить валидацию типов и обязательных полей до выполнения первого обращения к СУБД.
     - Складские служебные поля (`cell`, `cell_code`, `rack`) вырезаются из клиентского DTO заказа и разрешаются сервером по правилам складов.
  4. **Идемпотентность всех мутирующих операций**:
     - Обязательная передача и проверка заголовков `X-Idempotency-Key` / `Idempotency-Key` (UUIDv4).
     - Серверный регистр идемпотентности фиксирует статус и результат ответа на 24 часа. При повторе запроса возвращается сохраненный ответ без повторного создания заказа/проводки.
  5. **Монотонное версионирование остатков (CDC)**:
     - Любое событие обновления остатков из ERP содержит монотонный таймстемп `version_timestamp`. Пакеты с `version_timestamp <= current_version` отбрасываются.

* **Красные линии (DON'T / P0 Violations)**:
  - ❌ Синхронное ожидание ответа от 1С/ERP дольше 2.5 секунд на клиентских HTTP-потоках.
  - ❌ Прямая передача невалидированных параметров (`req.body`, `$_POST`) в логику и SQL.
  - ❌ Мутация состояния заказа/склада без валидного ключа идемпотентности.
  - ❌ Остановка работы веб-витрины (HTTP 500/502/504) при аварии на стороне 1С.

* **Definition of Done (DoD)**:
  - [x] Входной DTO валидирован типизированной схемой с возвратом понятного 400 Bad Request при несовпадении типов.
  - [x] Реализована проверка `X-Idempotency-Key` с сохранением ответа в регистре идемпотентности.
  - [x] Тест на таймаут ERP (>2.5 с): запрос завершается штатно со статусом `is_buffered_offline: true` и попаданием в Outbox.
  - [x] Проверка монотонности версии отсекает устаревшие вебхуки при нарушении порядка доставки пакетов.
  - [x] Логирование каждого вызова содержит сквозной `correlation_id`.

### БЛОК 2. ДВИЖОК ОСТАТКОВ И ХОЛДИРОВАНИЯ (HOLD ENGINE & STOCK ALLOCATION)

* **Суть блока и текущая планка**:  
  Управляет физическим распределением товара, резервированием под оптовых клиентов, списанием и аннулированием броней. **Целевая планка: Zero-Overselling (0% перепродаж) и Zero-Deadlocks (0% дедлоков в СУБД).**

* **Инженерный стандарт блока (DO)**:
  1. **Zero-Deadlock & Zero-Overselling Invariant**:
     - Резервирование остатков выполняется строго внутри атомарной транзакции СУБД (`create_order_atomic`).
     - Перед взятием блокировки строки номенклатуры обязательно сортируются по возрастанию SKU (`ORDER BY sku ASC FOR UPDATE`). Это математически исключает взаимные блокировки (Deadlocks).
     - Проверка доступного остатка: `IF free_stock < requested_qty THEN RAISE EXCEPTION ... ROLLBACK`.
  2. **Жизненный цикл холда (Hold Lifecycle & Strict TTL)**:
     - Каждая бронь создается с явным временем истечения `hold_expires_at`:
       - Экспресс-холд корзины: **30 минут**.
       - Оптовый резерв под выставленный счет: **24 часа**.
     - Фоновый демон-клинер (`api/cron/expire-holds.ts`) запускается по расписанию, находит просроченные резервы и атомарно возвращает их в `free_stock`.
  3. **Четкая сегрегация складских остатков**:
     - `total_stock` = `free_stock` (доступно к заказу) + `reserved_stock` (в активных холдах) + `to_ship_stock` (собрано/оплачено) + `consignment_stock` (забаланс).
     - На уровне СУБД действуют CHECK-констрейнты `free_stock >= 0` и `reserved_stock >= 0`.
     - Запрещено объединять запасы Центрального хаба (Склад 81, Астана) и региональных складов в один пул без явной складской адресации.
  4. **Мгновенная Realtime-нотификация**:
     - При снятии холда или резерва платформа рассылает событие высвобождения остатков через Realtime/WebSocket, актуализируя каталоги у менеджеров.

* **Красные линии (DON'T / P0 Violations)**:
  - ❌ Выполнение `UPDATE stock` без блокировки `FOR UPDATE` и сортировки SKU.
  - ❌ Возникновение отрицательного остатка в БД (падение CHECK-констрейнта).
  - ❌ Бессрочные холды (отсутствие `hold_expires_at` или отключенный клинер).
  - ❌ Смешивание собственного запаса и комиссионного товара в единую цифру без признака права собственности.

* **Definition of Done (DoD)**:
  - [x] Резервирование выполняется через хранимую процедуру с обязательной сортировкой `ORDER BY sku ASC FOR UPDATE`.
  - [x] Стресс-тест на 50 параллельных потоков на один и тот же SKU не создает оверселлинга и дедлоков.
  - [x] В БД активны CHECK-констрейнты неотрицательности остатков.
  - [x] Установлен жесткий TTL бронирования с автоматическим высвобождением через планировщик.

### БЛОК 4. ТОВАРНЫЙ УЧЕТ КОМИССИОНЕРОВ (CONSIGNMENT STORAGE)

* **Суть блока и текущая планка**:  
  Обеспечивает разделение права собственности между товарами собственного выкупа и товарами внешних комитентов на складе. **Целевая планка: Изоляция прав собственности и исключение ложных долговых обязательств.**  
  *(Примечание: блоки «Прозрачность начислений в реальном времени» и «Неизменяемость закрытых отчетов» временно опущены).*

* **Инженерный стандарт блока (DO)**:
  1. **Момент признания обязательства (Post-Sale Debt Recognition)**:
     - Приемка товара от комитента на склад оформляется со статусом «Ответственное хранение».
     - **В момент приемки кредиторская задолженность платформы перед комитентом строго равна 0.00.**
     - Финансовое обязательство (долг к выплате) начисляется **исключительно по факту продажи и отгрузки конечному покупателю** (событие `order.status = 'shipped'` / `'completed'`).
  2. **Сегрегация прав собственности в складском интерфейсе**:
     - Каждая единица номенклатуры комиссионера четко маркируется в UI:
       - «На ответственном хранении» (доступно для выставления в каталог).
       - «В резерве покупателя» (забронировано в заказе).
       - «Реализовано» (отгружено, передано покупателю).
       - «Брак / Возврат комитенту» (выведено из доступного оборота).

* **Красные линии (DON'T / P0 Violations)**:
  - ❌ Начисление долга перед поставщиком в момент поступления партии на склад.
  - ❌ Продажа комиссионного товара без привязки `supplier_id` и признака `is_consignment: true`.
  - ❌ Смешивание бракованного комиссионного товара с доступным складским остатком.

* **Definition of Done (DoD)**:
  - [x] Приходная накладная комиссионера создает забалансовые остатки без начисления финансового долга.
  - [x] Триггер начисления задолженности срабатывает только при переходе заказа в статус `shipped`/`completed`.
  - [x] В интерфейсе наглядно разделены статусы «На хранении» и «Реализовано».

### БЛОК 5. КОРПОРАТИВНАЯ БЕЗОПАСНОСТЬ И MULTI-TENANCY (SECURITY & RBAC)

* **Суть блока и текущая планка**:  
  Обеспечивает защиту коммерческой тайны (базы дилеров, индивидуальные скидочные матрицы, закупочные цены, условия договоров) и разграничение доступа между ролями. **Целевая планка: Банковский стандарт изоляции данных (Zero-Trust Multi-Tenancy & Anti-IDOR).**

* **Инженерный стандарт блока (DO)**:
  1. **Zero-Trust Identity & Anti-IDOR Invariant**:
     - Идентификаторы арендатора (`partner_id`, `supplier_id`, `client_id`, `role`) **никогда не принимаются из параметров клиента** (`req.body`, `req.query`, `$_GET`, `$_POST`).
     - Контекст авторизации извлекается строго из валидированного криптографического токена/серверной сессии (`authGuard.ts`).
     - Любая выборка или мутация данных содержит предикат принадлежности: `WHERE id = :id AND partner_id = :session_partner_id`.
  2. **100% Параметризация всех обращений к СУБД**:
     - Полный запрет конкатенации строк при формировании SQL.
     - Использование только подготовленных выражений PDO (`$stmt = $pdo->prepare(...)`) или типизированных Query Builder с биндингом параметров.
  3. **Полная изоляция контрагентов (Cross-Tenant Isolation)**:
     - Ни при каких условиях дилер или поставщик «А» не может получить доступ к данным, остаткам, ценам или заказам участника «Б».
     - Применение политик Row Level Security (RLS) в PostgreSQL.
  4. **Маскирование чувствительных данных (PII & Secrets)**:
     - В журналах аудита (`audit_logs`) номера телефонов, пароли и токены автоматически маскируются (`+7 *** *** 45 67`).

* **Красные линии (DON'T / P0 Violations)**:
  - ❌ Доверие параметру `partner_id` или `user_id`, переданному в теле запроса (IDOR-уязвимость).
  - ❌ Конкатенация строк в SQL (`"SELECT * FROM orders WHERE id = " . $id`).
  - ❌ Утечка оптовых скидок или цен одного дилера другому контрагенту.
  - ❌ Хранение открытых паролей, мастер-ключей или API-токенов в кодовой базе репозитория.

* **Definition of Done (DoD)**:
  - [x] Все эндпоинты защищены через `authGuard` / централизованный middleware сессий.
  - [x] Все SQL-запросы используют исключительно параметризованные Prepared Statements.
  - [x] Автотесты на подмену ID (IDOR fuzzing) подтверждают возврат 403 Forbidden / 404 Not Found.
  - [x] В коде отсутствуют захардкоженные токены, пароли и приватные ключи.

### БЛОК 6. КЛИЕНТСКИЙ СЛОЙ, UX И ИНТЕРФЕЙС БЕЗ БАГОВ (FRONTEND & PERFORMANCE)

* **Суть блока и текущая планка**:  
  Обеспечивает высокую скорость и плавность работы оптового каталога, таблиц остатков и корзины оформления. **Целевая планка: Субсекундный отклик интерфейса (Sub-50ms UX) без визуальных артефактов.**  
  *(Примечание: контекстные подсказки к финансовым метрикам опущены).*

* **Инженерный стандарт блока (DO)**:
  1. **Разметка модальных окон и оверлеев (React Portals Invariant)**:
     - Все элементы с позиционированием `fixed` и `absolute` (модальные окна, дропдауны, боковые шторки, полноэкранные спиннеры) монтируются **строго в корень документа** (`document.body` через `createPortal`).
     - Это гарантирует, что оверлеи никогда не будут сжаты, деформированы или обрезаны родительскими контейнерами с `max-w-*`, `overflow-hidden` или CSS `transform`.
  2. **Асинхронная неблокирующая загрузка (`Promise.allSettled`)**:
     - Компоненты загружаются независимо; отображение Skeleton Loaders вместо блокирующих полноэкранных спиннеров.
  3. **Защита от дребезга (Debounce & AbortController)**:
     - Все поля живого поиска по каталогу, артикулам и клиентам обязаны использовать Debounce с задержкой **300–400 мс**.
     - Предыдущий незавершенный поисковый сетевой запрос отменяется через `AbortController` во избежание состояния гонки (Race Condition).
  4. **Геометрическая целостность ковровых изделий (RugsUSA Standard)**:
     - Категорически запрещено использование `object-cover` для ковров и дорожек.
     - Только `object-contain` внутри контейнера с фиксированным соотношением сторон (`aspect-[4/5]`), сохраняющим кайму, орнамент и бахрому.
     - Минимальный размер кликабельных областей на тач-устройствах — **44 × 44 px**.

* **Красные линии (DON'T / P0 Violations)**:
  - ❌ Использование `object-cover` для изображений ковров и рулонов.
  - ❌ Размещение `fixed` модальных окон внутри контейнеров с ограничениями ширины (`max-w-*`) без выноса в портал.
  - ❌ Отсутствие debounce на строке поиска (сетевой шторм при вводе текста).
  - ❌ Блокировка UI длительными синхронными операциями в Main Thread (>50 мс).

* **Definition of Done (DoD)**:
  - [x] Все модальные окна вынесены через React Portal в `document.body`.
  - [x] Поиск по каталогу работает с Debounce (300-400 мс) и отменой устаревших запросов через `AbortController`.
  - [x] Изображения ковров используют `object-contain`, исключая обрезку краев изделия.
  - [x] Проверка `scripts/check-ui-standards.py` проходит со 100% результатом (0 ошибок).
