# 🗄️ База данных PostgreSQL, Миграции и Моделирование Данных

Данный документ устанавливает обязательные правила проектирования реляционной базы данных (PostgreSQL 15+ в Supabase), проведения миграций, оптимизации индексов и изоляции границ ответственности между порталом и WMS/ERP.

---

## 1. Регламент миграций (Safe & Zero-Downtime Migrations)

Любые изменения структуры базы данных оформляются исключительно через файлы миграций в директории `supabase/migrations/`.

### 1.1. Именование и структура файлов
Формат имени файла миграции строго стандартизирован:
`YYYYMMDDHHMMSS_<краткое_описание_на_английском>.sql`
Пример: `20260929160000_create_order_atomic_transaction.sql`

* Все миграции также регистрируются в консолидированном файле развертывания:
  `supabase/migrations/DEPLOY_ALL_ENTERPRISE_MIGRATIONS.sql`

### 1.2. Принципы безопасных миграций без простоя (Expand/Contract Pattern)
1. **Идемпотентность**:
   - `CREATE TABLE IF NOT EXISTS`
   - `ADD COLUMN IF NOT EXISTS`
   - `CREATE INDEX IF NOT EXISTS`
2. **Запрет деструктивных операций в один шаг**:
   - Категорически запрещено удалять (`DROP COLUMN`) или переименовывать колонку в один шаг. Сначала добавляется новая колонка, код переводится на ее использование, и только в следующем релизе удаляется старая.
3. **Безопасные блокировки**:
   - Создание тяжелых индексов на больших таблицах выполняется с ключевым словом `CONCURRENTLY` (без эксклюзивной блокировки таблицы на запись).

## 2. Нормализованная схема каталога ковров (RugsUSA Pattern)

Каталог ковровых изделий нормализован на два уровня: **Дизайн (коллекция/модель)** и **Вариант (размер/цвет/остаток)**.

```
┌────────────────────────────────────────────────────────┐
│                    product_designs                     │
├────────────────────────────────────────────────────────┤
│ id (UUID, PK)                                          │
│ collection_name (VARCHAR) — например, "Kashan"         │
│ title (VARCHAR) — "Kashan 3062A"                       │
│ country_of_origin (VARCHAR) — "Турция"                 │
│ pile_material (VARCHAR) — "100% Акрил"                 │
│ density_knots_sqm (INT) — 1 500 000                    │
│ created_at / updated_at (TIMESTAMPTZ)                  │
└───────────────────────────┬────────────────────────────┘
                            │ 1 : N
                            ▼
┌────────────────────────────────────────────────────────┐
│                   product_variants                     │
├────────────────────────────────────────────────────────┤
│ id (UUID, PK)                                          │
│ design_id (UUID, FK -> product_designs)                │
│ sku (VARCHAR, UNIQUE) — например, "3062A-CREAM-1623"   │
│ barcode (VARCHAR)                                      │
│ width (NUMERIC) — 1.6                                  │
│ length (NUMERIC) — 2.3                                 │
│ area_sqm (NUMERIC) — 3.68                              │
│ is_runner (BOOLEAN) — false                            │
│ size_cluster (VARCHAR) — 'M'                           │
│ base_price_usd (NUMERIC) — 145.00                      │
│ stock_quantity (INT) — 42                              │
│ warehouse_id (INT) — 81 (Основной Склад Астана)        │
└────────────────────────────────────────────────────────┘
```

### 2.1. Сверхбыстрый Trigram-поиск (GIN Indexes)
Для обеспечения поиска по неточным названиям, артикулам и цветам быстрее 50 мс используется расширение `pg_trgm`:
```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX IF NOT EXISTS idx_product_variants_trgm_sku 
ON product_variants USING gin (sku gin_trgm_ops);

CREATE INDEX IF NOT EXISTS idx_product_designs_trgm_title 
ON product_designs USING gin (title gin_trgm_ops);
```

## 3. Партиционирование таблиц аудита и логов

Таблицы `integration_audit_logs` и `audit_logs` накапливают миллионы записей операций синхронизации с ERP. Без партиционирования запросы к ним деградируют.

### 3.1. Стандарт ежемесячного партиционирования
- Таблица партиционируется по диапазону даты (`PARTITION BY RANGE (created_at)`).
- Секции создаются упреждающе минимум на 1–2 года вперед (см. `20260929150000_audit_partitions_2027.sql`):
```sql
CREATE TABLE IF NOT EXISTS integration_audit_logs_y2026m10
PARTITION OF integration_audit_logs
FOR VALUES FROM ('2026-10-01 00:00:00+00') TO ('2026-11-01 00:00:00+00');
```
* **Преимущество**: Запросы с фильтром по дате читают только нужный месяц (Partition Pruning), а старые данные архивируются без нагрузки на основной кластер.

## 4. Граница изоляции WMS-адресации (Warehouse Decoupling)

Один из важнейших архитектурных инвариантов проекта: **портал B2B не является WMS-системой**.

### ❌ Запрет утечки WMS-адресов:
- Поля физического адресного хранения ковров на стеллажах склада (`cell`, `cell_code`, `rack`, `shelf`, `tier`, `location`):
  1. **Категорически запрещено** создавать в схеме БД портала (`orders`, `order_items`, `products`);
  2. **Запрещено** принимать или отдавать в клиентских API-ответах;
  3. Очищаются серверными шлюзами перед отправкой в UI или сохранением.

### Обоснование:
Адресное хранение — динамическая прерогатива внутренней WMS/1C-системы склада (перемещение паллет, смена ячеек карщиком). Если портал начнет хранить ячейки, возникнет рассинхронизация и риски отправки неверных указаний сборщику.
